# Накопление новых спортивных данных

Подробная проверка сезонной статистики и таблиц, JS для браузера и целевой
сбор одного события: [docs/widget-data-audit.md](docs/widget-data-audit.md).

Отдельный сборщик для будущей прогнозной модели. Использует **код парсеров**
`nutakoe27-commits/finding` на зафиксированном коммите, без запуска сайта, Qwen
или импорта существующей базы. Старую базу `finding` не открывает и не изменяет.
Все записи поступают из новых обращений к источнику.

## Что сохраняется

| Данные | Источник и хранение |
| --- | --- |
| События, участники, турнир, время начала, стадия | Публичный клиент Winline; версии исходных записей |
| Коэффициенты и рынки | История основной линии; подробный парсер рынков для выбранных матчей |
| Статистика команд | Те же функции `collect_statistics` и `validate_statistics`, что в `finding`: StatsHub/Sportradar, сезонные разделы, таблицы, последние матчи, личные встречи, наблюдённый структурированный поток |
| Полные ответы виджета и числовые таблицы | `widget_json` сохраняет документы; `widget_data` — сезонные показатели по трём областям, строки таблиц с сезоном/группой/таймом, форму, историю и 28 состояний выбранных карточек |
| Завершённые результаты | Новые ответы ResultService; хранятся отдельно от предматчевых входов |
| Предматчевые входы | Событие, рынки, подтверждённая статистика и доступная история на указанное время |

Числа и текст сохраняются с исходными названиями, фильтрами, признаками
неполноты, временем наблюдения, SHA-256 и версией кода источника. Неизвестные
поля не превращаются в придуманные признаки. Новая версия статистики не стирает
предыдущую. Итоговые тексты и предпочтения генеративного ИИ не собираются.

Это **накопитель исходных данных**, а не обученная модель. `samples` — проверенные
по времени входы, но ещё не размеченная матрица для обучения: извлечение числовых
признаков, проверенное связывание с итогами и обучение будут следующим этапом.
Статистика может отсутствовать, быть обрезанной или содержать будущие встречи
внутри расписания; её полнота не предполагается. Перед обучением нужна проверка
полей, идентичностей участников и правил расчёта конкретного спорта/рынка.

## Установка

Нужны Linux, Python 3.12, Chromium и доступ к источникам. GPU и ключ Qwen не нужны.
Репозитории располагаются рядом:

```text
/workspace/doscbot
/workspace/finding       # только код, без подключения прежней базы
```

Если копии кода ещё нет, создайте отдельный чистый checkout, не меняя работающий
сервер `finding`:

```bash
git clone https://github.com/nutakoe27-commits/finding.git /workspace/finding
git -C /workspace/finding checkout --detach 5ac580951c91475c60747f92cf6ff1d5ae33494f
cd /workspace/doscbot
bash scripts/setup.sh
```

`finding-source.json` фиксирует ревизию. Сборщик отказывается использовать другую
ревизию или изменённые отслеживаемые файлы. Он не вызывает установщики и не читает
`.env` существующего приложения. Для другого расположения кода задайте
`FINDING_SOURCE_DIR`. Парсеры не копируются в проект и не расходятся с оригиналом.

Если системного Chromium нет, установите браузер для Playwright:

```bash
.venv/bin/python -m playwright install chromium
```

TLS-проверки остаются включены; при проблеме доверия настройте доверенный
сертификат прокси штатными средствами, не отключайте проверку сертификатов.

## Начать сбор с нуля

```bash
cd /workspace/doscbot
# Ограниченный первый проход: без архивных запросов, один предстоящий футбол.
bash scripts/collect.sh --once --history-days 0 --event-limit 1

# Постоянное накопление: следующий цикл через 300 секунд после предыдущего.
bash scripts/collect.sh --interval 300 --event-limit 5 --history-days 2
```

По умолчанию файлы создаются только в `.local/` этого проекта:

- `source/winline.sqlite3` — **новый** собственный архив исходного парсера;
- `dataset.sqlite3` — версии наблюдений, журнал запусков и предматчевые входы;
- `collector.lock` — запрет параллельных писателей.

Служба статистики оригинального `finding` использует обычный Chromium под Xvfb.
Для такого же режима подробного сбора на VPS установите `xvfb` и `xauth` и запускайте:

```bash
xvfb-run -a -s "-screen 0 1280x720x24 -nolisten tcp" \
  .venv/bin/python -m collector collect --headed --once --history-days 0 --event-limit 1
```

`--headed` меняет браузер подробных рынков/статистики; основной поток событий
сохраняет прежний режим. Контекст статистики использует `ru-RU` и
`Europe/Moscow`, как исходная служба. Режим не гарантирует доступ к провайдеру:
`blocked` остаётся ошибкой доступа, не успешной статистикой. Нужна проверка на VPS.

Для постоянного диска задайте `DOSCBOT_DATA_DIR` на **новый пустой каталог** вне
`finding`. Существующая чужая БД или заранее подложенный исходный архив вызывают
ошибку. Команды переноса/импорта старой базы в проекте отсутствуют.
Данные и виртуальное окружение исключены из Git.

Основной поток сохраняет наблюдённые события всех полученных видов спорта.
Подробные рынки/статистика по умолчанию собираются для футбола, до пяти событий
за цикл. `--sport all` разрешает доступные виды спорта. Очередь отдаёт приоритет
ещё не проверенным событиям, затем давно проверенным. Источник может не отдавать
статистику для каждого события. Это периодический сбор, не сохранение каждого
изменения линии. Предматчевые входы создаются только при наблюдённом предматчевом
событии до его начала, со статистикой не старше часа и без фактов из будущего.
Оригинальный парсер маркирует будущий виджет как `unknown`. Такая статистика
допускается только при подтверждённой связи через фактически наблюдённую ссылку
этого события и будущем времени начала. Исходное `unknown` сохраняется;
`eligibility` объясняет основание отбора. Явные live/finished в виджете или
структурированных данных исключаются. `last_run.details.sample_outcomes`
показывает причину сохранения или пропуска для обработанного снимка.

Исходный проход ограничен десятью минутами; при ошибках интервалы увеличиваются
до часа. Статусы `partial` / `source_error` / `error` требуют проверки; код 2 у
`--once` означает, что готовый предматчевой вход не подтверждён. Наличие PID,
созданной базы или пустого экспорта не подтверждает сбор. SIGINT/SIGTERM позволяют
завершить работу; ежедневное резервное копирование и контроль свободного места
для постоянного сервера настраиваются отдельно. Автоматического удаления истории нет.

## Проверка и выгрузка

```bash
.venv/bin/python -m collector status
.venv/bin/python -m collector export --kind samples --output .local/exports/inputs-001.jsonl
.venv/bin/python -m collector export --kind observations --output .local/exports/raw-001.jsonl
.venv/bin/python -m unittest discover -s tests -v
```

После обновления правил можно сформировать вход из уже собранного **новой
системой** снимка, без запросов к сайту и без изменения исходных наблюдений:

```bash
.venv/bin/python -m collector materialize --event-id 17139950 --dry-run
.venv/bin/python -m collector materialize --event-id 17139950
```

Подставьте ID из своего отчёта. Используется реальное время первого получения
статистики и только ранее полученный снимок рынков той же версии парсера.
Поздние изменения коэффициентов/результатов не попадают в исторический контекст.
Повторный запуск не дублирует вход. Доступен только собственный новый архив
сборщика, зарегистрированный в его метаданных; старая база `finding` не читается.

## Очередь результатов

Основной поток событий запускается без архивных запросов. После сохранения
предматчевых входов отдельная очередь запрашивает результаты выбранного спорта
(`--sport football` по умолчанию; `--sport all` — все доступные виды).
`--history-days 2` задаёт глубину по каталогу дат источника.

За цикл выполняется до четырёх заданий «спорт/день» (`--result-limit 4`), с
ожиданием ответа до 45 секунд (`--result-timeout 45`) и общим бюджетом очереди
три минуты. Каждый запрос получает отдельный браузерный контекст и WebSocket.
После тайм-аута контекст закрывается: поздний ответ не может быть присвоен
следующему дню или спорту. Следующее задание продолжает работу в новой сессии.
Подтверждённый отказ HTTP 401/403/429 останавливает дальнейшие обращения этого прохода.

Прогресс хранится в `doscbot_result_jobs` собственного нового исходного архива.
Успешный запрос последнего доступного дня повторяется не раньше чем через пять
минут, прежних дней — через час. Ошибки получают увеличивающуюся паузу от двух
минут до часа; очередь отдаёт приоритет ещё не проверенным заданиям.
Тайм-аут архива не увеличивает паузу успешного основного сбора до часа:
его следующий цикл сохраняет настроенный интервал. Ошибки основного источника
и подтверждённые отказы доступа по-прежнему увеличивают общую паузу.
Исходные результаты сохраняются прежним `winline.storage.save_results`, с историей
изменений и временем реального наблюдения. Задним числом они не попадают в входы.

В `last_run.details.results` смотрите `available_pairs`, `due_pairs`, `planned`,
`attempted`, `successful`, `failed`, `deferred`, `rows`, `new_versions` и причины
по отдельным `requests`. `source_exit_code` теперь описывает основной поток;
ошибки архива сохраняют общий статус `partial` и видны отдельно в `results`.
Нулевое число заданий при ещё действующем кэше не означает нового обращения
к источнику. Выполнение выбранной порции не подтверждает полноту всего архива.

Это изменение проверено на временных базах и искусственных ответах SDK, включая
запоздавший ответ в Chromium. Доступность и охват настоящего архива нужно
подтвердить следующим циклом на VPS; увеличение ожидания не гарантирует ответа.

Проверяйте свежий `last_run`, его состояние, причины ошибок и рост счётчиков
`event`, `market`, `market_document`, `team_statistics`, `result`, `samples`.
Экспорт создаётся только в новый файл. Тесты используют временные синтетические
данные и помеченную сохранённую фикстуру `finding`; в рабочую базу они не попадают.

## Сеть и постоянный запуск

Для источников нужны `winline.ru`, поддомены `*.winline.ru`,
`statshub.yunai.tech`, `statshub.sportradar.com`; для установки — GitHub и PyPI.
Если браузер покажет другой необходимый домен ресурсов, сначала проверьте отказ
и добавьте конкретный домен в настройки среды. Проверки доступа не обходятся.

В облачной среде живой процесс не сохраняется при публикации/перезапуске:
сборщик нужно запускать заново. Для круглосуточной работы используйте постоянно
работающий сервер, отдельный каталог данных и мониторинг `status`. Развёртывание
на существующем сервере `finding` этим проектом автоматически не выполняется.
