# Проверка полного состава данных виджета

Обновление: фиксированный обход 28 состояний заменён обнаружением карточек
и фильтров для пяти видов спорта. Текущий порядок проверки и сброса:
[multisport-restart.md](multisport-restart.md). Ниже сохранены факты исходного
футбольного отчёта и предыдущая схема обхода как контекст проверки.

## Что показал присланный файл

Исследован `doscbot-widget-68932518-1794460091937.json`, снятый
12 ноября 2026 года: 34 успешных JSON-ответа, четыре DOM-снимка,
обзор / отчёт / статистика. Матч — **Албания — Финляндия**, ID статистики
`68932518`. ID события Winline в файле отсутствует; диагностический файл
не импортируется в рабочую базу и не связывается с другим событием.

| Показатель сезона | Албания | Финляндия |
| --- | ---: | ---: |
| Победы | 3 | 2 |
| Забитые голы | 8 | 9 |
| Пропущенные голы | 3 | 2 |
| Обе команды забивали | 2 | 1 |
| Не забивали | 0 | 2 |
| Сухие матчи | 2 | 2 |

Значения JSON совпали с разметкой карточки. Найдены домашняя и гостевая
разбивки, средние показатели, 14 групп таблицы с 54 командами, по 20 прошлых
матчей участников, очные встречи, составы, травмы, судья и стадион.
`stats_season_teamscoringconceding/СЕЗОН/КОМАНДА/-1` содержит весь сезон;
ответ с последним параметром `3` — отдельную выборку последних матчей,
которую нельзя смешивать с сезоном или считать переключателем «Серия».
`stats_match_tableslice` содержит только участников: две строки при
`totalrows=4` не означают полную таблицу. Полная таблица приходит в
`stats_season_tables`. В файле есть явно обозначенный период `1`, но нет
ответов периодов `2` и `3`. Состояния «За матч» и «Серия» не переключались.
Отсутствие обрезки файла не доказывает полноту вариантов.

Порядковое место в `stats_formtable` относится к таблице формы всех групп;
это отдельное поле, а не место команды в собственной группе. ID сезонной
записи команды отличается от её `uid`: например, Албания — `10508147`
и `4690` соответственно. Эти идентичности сохраняются раздельно.
Проценты формы из разметки — 75 и 63 для выбранного окна «5»; они не являются
вероятностями победы. Коэффициенты самой Winline собираются прежним путём
через её линию и рынки; `odds_ukformat` в отчёте виджета не подтверждает
получение коэффициентов Winline.

## Новое сохранение и обход

Сборщик теперь добавляет `widget_data` к наблюдениям `widget_json`.
Первое содержит числовые показатели сезона по областям total/home/away,
строки таблиц с сезоном, группой, ID периода и команд, форму, историю и
происхождение каждого документа. Второе сохраняет полные структуры ответов,
включая ещё не нормализованные составы, игроков и прочие документы.
Нет значения в источнике — сохраняется `null`; нулевое значение остаётся нулём.
Время получения и время формирования документа провайдером различаются.

После прежнего подробного прохода сборщик открывает наблюдённые ссылки
того же iframe и собирает 28 состояний карточек:

- сезон: «Итоги / За матч / Серия» × «Общее / Хозяева — Гости»;
- таблица обзора: «Всего / Хозяева / Гости / Завершен» × три периода;
- полная таблица статистики: четыре области;
- форма: «Общее / Хозяева / Гости» × «5 / Сезон».

Клики ограничены известной карточкой `data-testid` и подтверждаются
`aria-pressed`. Снимок ожидает завершения наблюдаемых запросов виджета и
стабилизации текста. Одинаковые числа в разных состояниях допустимы.
Неизвестные или отсутствующие фильтры не угадываются: причина попадает
в `views.missing`. Дополнительный обход ограничен 45 секундами на матч;
он может увеличить длительность цикла.

`last_run.details.widget_coverage` показывает покрытие по событиям, а
`widget_data.payload.views.groups` — ожидаемое и полученное число состояний.
`coverage.complete` относится только к перечисленным карточкам и периодам;
это не подтверждение всех возможностей сайта или готовности обучающей выборки.
Успех всего цикла `state=ok` не заменяет эту отдельную проверку.
В отсутствие блока его состояние остаётся неполным: без живого сравнения
нельзя утверждать, что блок отсутствует у провайдера, а не пропущен парсером.

Новые записи пока хранятся отдельно от прежних `samples`. Обучение потребует
выборки версий, полученных до старта матча, и проверки связи с итогами.
Позднее загруженный файл нельзя задним числом превратить в предматчевый вход.

Диагностика браузерного файла без сети и без открытия баз:

```bash
.venv/bin/python -m collector inspect-widget \
  --input /путь/doscbot-widget-68932518-1794460091937.json \
  --output /tmp/widget-68932518-inspected.json
```

Результат создаётся новым файлом. Команда не перезаписывает существующий файл.
Полный исходный отчёт не хранится в Git; тестовый пример сокращён до
необходимых публичных полей и двух карточек.

## Обновление и проверка на VPS

Новых зависимостей нет. Обновление не требует удаления или переноса данных:

```bash
sudo systemctl stop doscbot-collector.service
cd /opt/doscbot-collector/app
git pull --ff-only origin feat/fresh-sports-collector
sudo systemctl start doscbot-collector.service
sudo journalctl -u doscbot-collector.service -n 5 --no-pager
```

После завершения следующего цикла прочитайте последний подробный отчёт:

```bash
sudo -u doscbot-collector -H \
  /opt/doscbot-collector/app/.venv/bin/python \
  /opt/doscbot-collector/finding/winline/query.py \
  --database /var/lib/doscbot-collector/data/dataset.sqlite3 \
  sql "SELECT entity_id AS event_id, observed_at,
    json_extract(payload, '$.statistics_id') AS statistics_id,
    json_extract(payload, '$.coverage') AS coverage_json,
    json_extract(payload, '$.views.groups') AS filters_json,
    json_extract(payload, '$.views.missing') AS missing_json
    FROM observations WHERE kind='widget_data' ORDER BY id DESC LIMIT 1"
```

Живой проход новой версии на VPS ещё требуется. Офлайн-проверки включают
реальные JSON/разметку присланного файла, отложенное обновление значений,
подтверждение фильтров и переходы между вкладками того же матча. Из текущей
облачной среды доступ к Winline/провайдеру не разрешён активной политикой сети.

пары `event_id`/`event_url` остаются `null`, привязка — `statistics_page_only`.
Данные `68932518` никогда автоматически не приписываются событию `17139995`.

## Что уже изменено в сборщике

`collector.widget_capture.WidgetCapture` сохраняет отдельные наблюдения
`widget_json`: JSON-ответы, которые сам виджет получает при обычном открытии и
переключениях. Запрос должен принадлежать iframe нужного ID статистики и идти
на известный домен виджета/его данных. Сохранение начинается перед навигацией
на статистику, поэтому включает первоначальные ответы.

Сохраняются исходные структуры публичных спортивных данных: в том числе
документы сезона, командных показателей, таблиц и игроков, если источник их
передал. Это расширяет прежнюю проекцию `match` + `participants.matches`.
Ответы без Content-Length тоже поддерживаются. Cookies, заголовки авторизации
и значения параметров URL не выгружаются; поля с признаками учётных данных
удаляются. На ответ действует предел 2 МиБ, на матч — 16 МиБ и 200 ответов;
пределы и пропуски явно отражаются в отчёте.

В `last_run.details` появились `widget_json` и `widget_capture_states` по
событиям. `captured` означает сохранение наблюдённых JSON, а не полный обход
всех фильтров. `partial` отмечает ограничения или ошибки сохранения;
`no_json_observed` не заменяет подтверждение полноты. Рабочие `samples`
сохраняют прежние проверенные входы: новая числовая проекция находится отдельно
в `widget_data`. Новых внешних запросов этот наблюдатель
сам не делает. Старая база `finding` не используется.

## Дополнительный сбор в браузере при расхождениях

Присланного файла достаточно для текущей реализации. Если проверка на VPS
покажет расхождение со страницей, дополнительный сеанс даст структуру JSON,
разметку строк и состояния переключателей именно проблемного блока. Прямой HTTP
клиент можно выбрать после проверки доступности и эквивалентности наблюдённых
запросов. До этого сохраняется рабочий Playwright-путь.

1. Откройте страницу статистики нужного матча в Chrome, например
   https://winline.ru/stats/match/68932518 или исходную `75512542`.
2. Откройте DevTools → Console (`Cmd+Option+J` на Mac).
3. В списке контекстов вместо `top` выберите iframe
   `statshub.yunai.tech` или `statshub.sportradar.com` с путём
   `/winline/ru/match/ID` с ID текущей страницы. Проверка `location.origin + location.pathname`
   должна показать провайдера, а не `winline.ru`.
4. Скопируйте весь `scripts/widget-probe.js` и выполните в этом контексте.
   ID определяется из этого пути; контекст `top` отклоняется. Если в том же
   окне уже шла запись другого матча, сначала сохраните её и перезагрузите
   страницу, чтобы не смешивать два события.
5. На «Обзоре» переключите доступные состояния сезонной статистики:
   «Итоги / Общее», «Итоги / Хозяева — Гости», «За матч / Общее»,
   «Серия / Общее». После каждого действия подождите 2–3 секунды.
6. В таблице переключите «Всего / Хозяева / Гости / Завершен» и, если
   присутствуют, «Результат / 1-й тайм / 2-й тайм». Нужны только элементы
   этой страницы, без перехода на другой матч. Для диагностики достаточно
   примеров каждого типа переключателя; полный перебор автоматизируется после
   проверки схемы и привязки полей.
7. Выполните `await doscbotProbe.download()` и сохраните JSON обзора.
8. Перейдите на вкладку «Статистика», повторите доступные переключения и
   сохраните второй файл. Если после полной навигации `doscbotProbe` исчез,
   снова выберите правильный iframe и вставьте скрипт. Уже сохранённый файл
   содержит предыдущую вкладку. Не перезагружайте страницу до первого экспорта.
9. Прикрепите полученные JSON к чату. Полный HAR, cookies и ключи не нужны.

Если загрузка из iframe заблокирована браузером, используйте в Console
`copy(await doscbotProbe.report())` и сохраните скопированный текст в JSON-файл.
`doscbotProbe.status()` показывает количество ответов и снимков, пропуски и
ограничения. `doscbotProbe.mark('описание выбранных фильтров')` добавляет снимок
вручную. `doscbotProbe.stop()` восстанавливает исходные fetch/XHR и снимает
наблюдение; запросы приложения продолжают работать.

Скрипт только наблюдает запросы самого виджета, читает публичную разметку
этого iframe и по команде создаёт локальный файл. Он не делает повторных
сетевых запросов и не отправляет отчёт в сторонний сервис. Первые запросы,
завершившиеся до вставки скрипта, помечены как не наблюдённые; доступные
`__NEXT_DATA__`/`__NUXT__` и текущая разметка фиксируются отдельно.
При SPA-переходах запись может продолжиться в том же окне; при полной
перезагрузке iframe её необходимо установить заново.

## Целевая проверка на VPS

После обновления кода остановите только новую службу сборщика и выполните
один проход в его новом каталоге данных:

```bash
cd /opt/doscbot-collector/app
sudo -u doscbot-collector -H env \
  FINDING_SOURCE_DIR=/opt/doscbot-collector/finding \
  DOSCBOT_DATA_DIR=/var/lib/doscbot-collector/data \
  PLAYWRIGHT_BROWSERS_PATH=/var/lib/doscbot-collector/browsers \
  xvfb-run -a -s "-screen 0 1280x720x24 -nolisten tcp" \
  .venv/bin/python -m collector collect --headed --once \
  --history-days 0 --event-id 17139995 --event-limit 1
```

Затем запустите свою `doscbot-collector.service` снова. Флаг `--event-id`
не подменяет отсутствующий/начавшийся матч другим. Этот проход проверяет
подробный виджет, а не архив результатов: проверка архива требует обычного
режима с `--history-days 2`.

Полноту каждого живого прохода следует проверять по `widget_coverage` и
`views.missing`: разные матчи предоставляют разные блоки. Проверки перехвата
fetch/XHR, структуры, привязки iframe и ограничений не заменяют такую проверку.
